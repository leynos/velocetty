# Architectural decision record (ADR) 006: Oxlint plug-in strategy

## Status

Accepted.

## Date

2026-10-20

## Context and problem statement

Biome provides formatting and general lint checks. The repository also has
package-boundary checks, but it does not run Oxlint. The requested Unicorn and
`ai-deslop` rule sets add syntax-aware checks for correctness, maintainability,
and evidence at TypeScript boundaries.

The rule set must be stable across installs, work alongside Biome, and preserve
documented configuration and session contracts. Oxlint's JavaScript plug-in
interface is marked alpha, so compatible tool versions must be pinned and the
enabled rules must be reviewable.

## Decision drivers

- Keep Biome as the formatter and owner of its existing general lint rules.
- Run the recommended Unicorn and `ai-deslop` rules in the existing lint gate.
- Pin the linter, JavaScript plug-in, and type-aware backend.
- Preserve documented behaviour where a style rule conflicts with a contract.
- Prefer Unicorn when a Unicorn rule conflicts with a Deslop rule.

## Decision outcome

Install Oxlint and its type-aware backend at exact versions. Enable the
built-in Unicorn plug-in and the `ai-deslop` JavaScript plug-in. `unicorn`
ships with Oxlint, so its version is fixed by the Oxlint pin.

| Component         | Version    | Role                                |
| ----------------- | ---------- | ----------------------------------- |
| `oxlint`          | `1.82.0`   | Linter and built-in Unicorn plug-in |
| `ai-deslop`       | `0.4.8`    | Recommended Deslop JavaScript rules |
| `oxlint-tsgolint` | `7.0.2004` | Type-aware lint backend             |

Table 1: exact versions in `package.json` and `bun.lock`.

Bun is pinned to `1.4.3` in `package.json`, following the requested 1.4.x
toolchain. The lockfile was regenerated with that version.

The CI workflows no longer repeat that version as a literal. Each
`oven-sh/setup-bun` step reads `bun-version-file: package.json`, so the runner
and the repository cannot disagree about which Bun wrote `bun.lock`. The two
failures this avoids are worth recording, because both are silent.

A Bun older than `1.4.3` cannot parse the regenerated lockfile. It reports
`Unknown lockfile version`, then warns `Ignoring lockfile` and re-resolves the
entire dependency tree from the ranges in `package.json`. Bun 1.3.11 resolved
`normalize-url` to the ESM-only 7.x release, which `electron-link` then bundled
into the V8 startup snapshot as raw `export` syntax and failed to parse. The
lockfile on disk had pinned the CommonJS 6.1.0 that the snapshot is written
against, so the pinned tree was correct and only the unpinned runner broke.
Repetition also let the pin drift: `bun.lock` and `package.json` moved to
`1.4.3` while the workflow literals stayed at `1.3.11`.

A second, unrelated silent failure came from a generated file that the rules
required changing. Making the config boundary honest replaced the `unknown`
plugin-settings value type with a concrete JSON value and widened
`rawConfig.config` to `Partial<configOptions>`. Both types feed
`shared/schemas/schema.json`, which `typescript-json-schema` names after the
TypeScript types it derives from, so the rename rewrote the `$ref` that
`app/config/json5-config.ts` read at module load. That module hardcoded the
definition name and crashed on import, aborting three test files on every
platform.

The stale committed copy hid the change. Both schema files are tracked but
regenerated by `postinstall`, so a working tree that had already regenerated
them passed locally while CI regenerated them on checkout and failed. The fix
reads the definition name back out of the schema's own `$ref` rather than
naming it, and accepts either an `allOf` or an inline definition, so a future
type rename cannot break config loading. Rerunning the generator is now
byte-stable, which is the check that would have caught this before pushing.

Every supported rule in Oxlint's Unicorn recommended profile and every rule in
the `ai-deslop` recommended profile is listed explicitly in
[`.oxlintrc.json`](../.oxlintrc.json). Oxlint's accumulating-spread rule is
also enabled as recommended by Deslop. All Oxlint categories are off, so an
upstream category change cannot silently add or remove rules. Type-aware
analysis is enabled for the recommended rules that require it.

The Deslop `no-runtime-typeof` rule permits checks inside named type guards.
Those guards establish a reusable parser contract; checks outside them still
need to decode input at its I/O boundary. Type-aware analysis is enabled for
the Deslop rules that inspect TypeScript types. The root and app configs use
TypeScript 7-compatible path and module-resolution settings. The root config
also enables `strictNullChecks`, which the recommended
`typescript/no-unnecessary-condition` rule requires; the dedicated typecheck
config keeps its existing strictness settings.

`make lint` runs Oxlint after Biome and the package-boundary check. Biome keeps
its current responsibilities and settings. The new configuration introduces no
overrides for Biome rules or TypeDoc output.

## Disabled rule

Three rules are disabled globally for documented contract or plug-in conflicts:

- `unicorn/no-null`: the configuration layering contract says an explicit
  `null` resets a value, and the public session and configuration types include
  nullable values. Replacing these values with `undefined` would change
  configuration merging or serialized messages. See the
  [layering contract](../app/config/layering.ts#L48), [session types](../shared/src/types/common.ts#L40),
  and [configuration types](../shared/src/types/config.ts#L56).
- `deslop/no-unknown-parameters`: the transport guidance requires untrusted IPC
  responses to enter the transport boundary as `unknown` and be validated with
  Zod before reaching application code. This rule rejects that required
  boundary parameter type. See
  [transport abstraction practice](developers-guide.md#transport-abstraction-practice).
- `deslop/no-reflect-apply`: this directly conflicts with
  `unicorn/prefer-reflect-apply`; the Unicorn rule takes precedence.

`unicorn/prefer-event-target` remains enabled except at the specific Node
event-emitter integration points. The Linux updater implements Electron's
`AutoUpdater` API, `Session` is passed to the existing session-class plug-in
hook, and the RPC bridges expose the shared `TypedEmitter` contract using
Node's synchronous emitter semantics. The RPC server test double also models
Electron's `WebContents` emitter. These sites carry inline explanations; the
rule remains active for other code.

`unicorn/number-literal-case` is disabled only for two files because Biome's
existing formatter writes hexadecimal digits in lowercase, while this rule
requires uppercase digits. The conflict is limited to
[the ELF header checks](../bin/mksnapshot-wrapper.js#L40) and
[the Unicode escape bound](../app/runtime/plugin-runtime-json5-parser.ts#L331).

The snapshot loader models module exports as `SnapshotModuleExport` and module
definitions using the `electron-link` callback contract, so its dynamic module
cache retains a concrete type without widening exports to `unknown`. The
snapshot bootstrap requirement is recorded in the
[esbuild migration ADR](adr-002-replace-webpack-babel-with-esbuild.md#required-plugin-and-bespoke-transform-analysis).

When a construct is reported by both plug-ins, its implementation must satisfy
both rules; if their preferred forms conflict, the Unicorn form takes
precedence. `deslop/no-reflect-apply` is the current mutually exclusive pair.

`bin/rimraf-standalone.js` is a generated vendored script and remains excluded
from both Biome and Oxlint. Its source is maintained by the `rimraf` package.

## Addendum: what the new rules revealed about the gates

Enabling the profiles surfaced a gap between the gates that run locally and the
projects those gates actually compile. The first push of this change was green
on `make check-fmt`, `make lint`, `make typecheck`, and `make test`, and red in
CI on `bun run build:shared`.

The four local gates run `tsconfig.typecheck.json`. That project includes
`app/`, `lib/`, `cli/`, `typings/`, and `shared/src/`, and relaxes
`tsconfig.base.json` with `strict: false`, `noUncheckedIndexedAccess: false`,
`noPropertyAccessFromIndexSignature: false`,
`exactOptionalPropertyTypes: false`, `noImplicitOverride: false`,
`useUnknownInCatchVariables: false`, and `verbatimModuleSyntax: false`. The
`shared/`, `frontend/`, `backend/`, and `app/tsconfig.build.json` projects each
compile against the strict base and sit outside every gate, as do the
`build/esbuild/` bundle and the `test/` tree. CI runs them; the local gate set
does not.

That gap is why the three findings below are recorded here rather than in the
commit that fixed them. All three are the same class of defect: code that a
relaxed compile accepts and a strict one rejects.

- A registry declared with `satisfies` keeps its literal key type, so a
  dynamic `string` key cannot index it.
  `shared/src/constants/config-reloadability.ts` now narrows through a small
  lookup helper instead of indexing the registry directly.
- `shared/src/config/json5-config.ts` reconstructed a sorted object by
  mutating an accumulator, which the new rules report and which
  `noUncheckedIndexedAccess` compounds. It now sorts entries and rebuilds with
  `Object.fromEntries`, keeping the key comparator a named predicate.
- `shared/src/runtime/golden-path-demo.ts` read an optional settings field
  through an index signature, which `noPropertyAccessFromIndexSignature`
  rejects.

Two regressions the type checker could not see came from the same commit and
are recorded with their fixes. Anchoring every asset path in
`app/config/paths.ts` to `app.getAppPath()` dropped a `config` path segment, so
four paths pointed outside the build output; the paths are restored and
`test/unit/config-paths.test.ts` pins them against the layout the build copies.
`lib/containers/hyper.tsx` lost an optional call on `getActiveTerm()`, which
can miss while a session's term group is still mounting; the accessor now
returns `Term | undefined` so the compiler enforces the guard at every caller.

The lint profiles also changed how the CLI reports a failure. The rules
replaced the CLI's `process.exit(1)` calls with throws, and every throw now
reaches a single top-level reporter; that reporter printed `error.stack`, so
failures a user causes and can act on — a missing plugin name, an unlaunched
Hyper, a mistyped directory — gained a stack trace framing the report in the
CLI's own internals. `cli/index.ts` now throws an `ExpectedFailureError` for
those three and prints only its message, keeping the stack for unexpected
defects. The named subclass, discriminated with `instanceof`, follows the
[`InvalidSessionExtraOptionsError`](../app/ui/window.ts#L33) that separates the
same two cases for the renderer.

The general lesson is that a green local gate set is evidence about the
projects it compiles and nothing more. The
[developers' guide](developers-guide.md#local-gates-do-not-cover-the-whole-build-surface)
lists the omitted projects and the commands that cover them.

## Addendum: the emitted-file leak and the mirrored rules

Two further consequences of this change were found only in CI, and both are
recorded here because neither is visible to any local gate.

### A type import in a shared typings file emits the imported project

`app/tsconfig.build.json` lists `../typings/runtime-globals.d.ts` in its
`include`. That listing is the whole build surface: a project's included files
decide its program. Adding
`import type {SnapshotRuntimeResult} from '../lib/v8-snapshot-util'` to that
typings file pulled a `lib/` source file into the app build program. The
compiler then computed that file's output path from the source file rather than
from `outDir`, and emitted `lib/v8-snapshot-util.js`, `.d.ts`, and `.js.map`
**in place**, beside the sources. The emitted JavaScript was not runnable: it
carried the bare specifier `require('@shared/types/guards')`, which nothing
resolves under `dist/app`.

`bunx tsgo --project app/tsconfig.build.json --outDir /tmp/probe --listEmittedFiles`
is the diagnostic. `--listEmittedFiles` without an `--outDir` override emits
nothing at all and reports nothing, so the override is what makes the check
meaningful. Of 165 emitted files, exactly three landed outside the two output
trees, and all three were that one source file.

The declaration now lives in `lib/v8-snapshot-util.ts`, beside the type it
holds, so the shared typings file imports nothing. The rule that follows is
narrower than "avoid imports in `.d.ts` files": a `../`-relative file in an
`include` list may reach only files already inside that project, because only
those have an output path the compiler derives from `outDir`.

### The rules are satisfied by mirrored modules, not by suppressions

The alias rule above leaves `app/` modules compiled into `dist/app/` unable to
import shared runtime values. The new rules then required guards, identifiers,
and reloadability constants in those same modules, and the honest way to
satisfy both was to mirror the shared implementations app-locally rather than
to disable the rules at each site:

- `app/utils/runtime-guards.ts` mirrors the shared type guards.
- `app/config/reloadability-registry.ts` mirrors the shared reloadability
  registry. `CURSOR_STYLE_KEY` is spelled out as a local constant because the
  shared name is a runtime value, and the entry uses it as a computed key so the
  `no-shape-in-symbol-names` rule accepts the name.
- `app/utils/shared-ids.ts` carries app-local identifier constructors.
- `app/config/json5-config.ts` reads its Ajv definition name back out of the
  generated schema rather than importing it.

A mirror can drift from its original, so each is pinned by a parity test that
compares the two decision tables value by value rather than restating the
expected results. `test/unit/app-runtime-guards-parity.test.ts` and
`test/unit/app-reloadability-parity.test.ts` assert whole-object equality
against the shared registries over a fixed probe set.

The mirrored guards recurse where the inline checks they replaced were shallow.
Every config value reaching them has already been through a JSON5 parse and an
Ajv schema validation, or was written as a literal `{}`, so no non-JSON value
can arrive. The recursion matches what `stringifyConfig` and `sortKeys` already
require. The related changes in the same commit are equally
behaviour-preserving: `Object.entries(...).sort()` became `.toSorted()` on an
array that was already a fresh copy, and `issues[0]` became `issues.at(0)`.

### An undetermined pack architecture keeps the default snapshot

The macOS job packs both `x64` and `arm64` on an arm64 runner, but
`bin/run-v8-snapshot.js` generates only `arm64` artefacts there. The copy hook
resolved the architecture from the `afterPack` context and fell back to
`process.arch` when that context did not carry one. On that runner the fallback
returned the host's architecture, so the `x64` bundle silently received the
`arm64` snapshot. That is a wrong-architecture copy, which Electron cannot
load, and it is indistinguishable from success in the log.

`resolveContextArch` now returns `undefined` rather than the host architecture,
and the hook logs and keeps Electron's bundled default snapshot, which is the
supported fallback. Absent artefacts and an undetermined architecture are
handled the same way; a partially written cache directory stays a hard error,
because that is a failed generation rather than an unsupported host.
`test/unit/cp-snapshot.test.ts` covers all three cases.

## Addendum: the entry-point split and the load-order contract

Splitting `app/index.ts` into `app/index.mts` and `app/start.ts` in the commit
that introduced the lint profiles also reordered module evaluation, and the
reordering broke the development app on every platform.

The two files depend on each other in a way the type checker cannot see. Two
modules read the configuration while their own module bodies run:
`app/plugins.ts` resolves the plugin and local-plugin lists, and
`app/session.ts` reads `useConpty`. Node evaluates a required module as soon as
it is required, so whichever statement in `app/start.ts` reaches those modules
runs before any later statement in that file — including the `config.setup()`
call that used to sit among them. On `main` the ordering held by accident:
`config.setup()` sat textually above `import * as plugins from './plugins'` in
a single entry file, because an import there was free to sit below a statement
that had to run first. The split collected every import into one block at the
top of `app/start.ts`, and the plugin-list read moved ahead of setup with it.

What made the reordering visible was a separate, deliberate improvement. The
same commit replaced `let cfg: parsedConfig = {} as any` with
`let cfg: parsedConfig | undefined` and a `getCurrentConfig()` accessor that
throws `Configuration has not been initialized`. On `main` the unsafe
placeholder made the early read return `{plugins: [], localPlugins: []}` and
the app started; on this branch the same read throws, and the entry point
surfaced it as
`Failed to start Hyper. Error: Configuration has not been initialized` with a
`getPlugins` frame in `dist/app/plugins.js`.

The fix moves the initialization to the entry point. `app/index.mts` imports
`./config.js`, calls `config.setup()`, and only then imports `./start.js`, so
the order is stated once, where the process starts, rather than depending on
where a statement sits relative to an import several modules down.
`test/unit/app-startup-order.test.ts` pins both halves: the setup call precedes
the `./start.js` import, and `app/start.ts` does not reintroduce it below its
own imports.

Two properties of this failure are worth recording beyond the fix. It is
invisible to every local gate, because `tsconfig.typecheck.json` type-checks a
program whose module graph is a compile-time notion; evaluation order is a
runtime property of the emitted CommonJS. And the packaged lane's E2E test
passed on macOS throughout, because its CI fallback tolerates an absent
`[e2e] renderer-ready` marker when the exit code is still null, which is the
state an `app.quit()` before ready leaves behind. Only the development lane,
which requires the marker, reported the truth. A green lane next to a red one
was evidence about the lane, not about the app.

## Known risks and limitations

- Oxlint's JavaScript plug-in interface is alpha. The exact pins keep the
  current configuration reproducible; upgrades require rerunning the lint and
  typecheck gates.
- `ai-deslop` brings `@oxlint/plugins` as a runtime dependency. Its compatible
  version is recorded in `bun.lock` and is upgraded with the plug-in.
- The recommended rules may expose existing code that needs a real correction.
  New global disables require a documented conflict with project guidance,
  Biome, TypeDoc, or the other plug-in.
- The Bun pin is a single source of truth only while every workflow derives its
  version from `package.json`. Reintroducing a literal `bun-version` there
  restores the drift this record describes.
- The local gate set compiles only `tsconfig.typecheck.json`'s projects. A
  change to `shared/`, `frontend/`, `backend/`, or the app build config must
  also run `bun run build:packages` and
  `bunx tsgo --project app/tsconfig.build.json` before it is pushed.
- Mirrored app-local modules are a deliberate duplication. Each one is pinned
  by a parity test, and a change to a shared implementation must carry the
  mirror and its parity test in the same commit.
- `cli/index.ts`, `lib/components/terms.tsx`, and `lib/containers/hyper.tsx`
  sit outside every strict project, so they are type-checked only at
  `strict: false`. This is a pre-existing gap that the lint profiles surfaced
  rather than introduced.
